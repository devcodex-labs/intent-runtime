# 1. 需求背景

需要一个可以独立复用的意图结构化模块，把用户的自然语言表达整理成含义清楚、能够被后续处理方共同理解的结果。

用户的表达经常存在口语、重复、错别字、省略、上下文指代、纠正和多目标混合。一个请求还可能同时包含主要目的、多个动作、禁止事项、输出要求、确认前提和条件分支。只提取一个动作名称或生成一段摘要，容易遗漏这些信息。

不同调用方还需要不同的业务信息。如果每个调用方分别定义通用意图字段和提取方式，就容易出现含义不一致、重复配置和无法复用的问题。

因此，需要同时具备统一的默认意图表达和可配置的业务扩展能力，并能保留用户原文，让调用方检查整理是否改变了原意。

# 2. 需求目标

模块需要实现以下效果：

1. 清楚表达用户本轮实际希望做什么，而不把背景愿望、引用内容或自行推断的实施步骤当成当前任务。
2. 保留主要目的、各条有效意图、动作对象、要求、限制、处理前提及需要澄清的信息。
3. 同时提供原始文本和整理后的文本，便于理解和核对。
4. 支持调用方用原生 schema-dsl 定义扩展信息，并在每次调用时选择需要提取的内容。
5. 根据调用方配置的语言表达结构化结果，保持固定字段和枚举含义一致。
6. 在信息不足、存在冲突或无法满足所选业务定义时明确反馈，不用猜测填满结果。
7. 让简单请求可以直接使用，也让多意图和上下文场景能够保留完整语义。

# 3. 功能定位

这是一个负责“理解并表达用户当前意图”的通用模块。

它从用户本轮原始文本及调用方提供的相关上下文中，输出默认意图信息和所选业务扩展信息。后续处理方可以据此继续沟通、判断适用能力或安排工作。

模块本身不执行动作，不调度任务，不验证真实系统权限，也不保证目标系统具有完成某个动作的能力。识别结果中的状态不是执行进度。

模块不自动读取历史会话、项目文件、知识库或其他外部资料。需要参与理解的上下文由调用方提供。文本中的文件路径、网址和引用是意图信息，不自动触发资料读取。

# 4. 核心需求

## 4.1 统一配置与重复使用

调用方可以统一配置结构化结果的表达语言和扩展信息定义。同一配置能够用于多次解析，不必每次重复提供。

配置入口采用已确认的 `new Intent(config)` 形式。语言与扩展定义均可以省略：

- 未配置语言时，结构化说明默认使用英文，语言值为 `en`。
- V1 接受能指定结构化输出语言的登记有效 BCP 47 标签；语言配置合法性与模型效果验证分开记录。
- 仅需要默认意图时，可以省略 Schema 或提供空定义，默认能力保持完整。

具体示例见附录 A。

## 4.2 默认意图表达

无论本次是否提取扩展字段，默认结果都需要能够表达：

- 本轮原始文本及整理后的文本。
- 本轮主要目的。
- 适用于整个请求的要求。
- 各条有效意图及其动作对象、局部要求、状态和必要说明。
- 用户明确禁止的全局行为。
- 本次选中的业务扩展信息。

没有相关内容时，应使用约定的空结果，而不是编造内容。没有操作意图时允许意图列表为空；没有主要目的时允许主要目的为空。

## 4.3 主要目的与有效意图识别

需要区分用户的背景愿望、本轮请求、已经发生的事实、后续条件动作和第三方提出的建议。

例如，“我想创建一个模块，你先审查需求，不要开发”，当前请求是审查需求。不能把创建模块直接当成当前需要实施的动作。

用户明确指出主要目的时，需要保留。多个目标同等重要或缺少主次依据时，不强行选择第一条作为主要目的。

## 4.4 多意图与多对象

一个请求包含多个实际动作时，需要分别保留。

一个动作涉及多个对象，不必仅因对象数量而拆成多个意图。例如“比较 A 和 B”可以是一条比较意图。

同一动作在不同阶段再次出现时，不能当作赘述去重。例如“先测试、再修改、最后再测试”，两次测试均是有效要求。

用户只提出一个结果目标时，不自行补出扫描项目、选择方案、修改代码、测试和发布等实施安排。用户明确提出这些动作时才作为请求内容保留。

## 4.5 动作分类与业务含义保留

动作类别需要固定，并按照用户要求达到的直接结果分类，不按后续使用的工具分类。

获取已有信息、分析判断、生成新内容、修改已有内容或状态、删除对象、运行操作任务，应按各自类别表达。执行类别不作为所有有副作用动作的通用兜底。

通用类别不能代替具体业务含义。例如“取消订单 A”可表达为状态修改，但必须保留“取消”，不能只剩下“修改订单 A”。具体业务动作保留在对象描述或该意图的要求中。

动作明确但不属于现有类别时使用其他类别；已经知道用户提出请求、但动作尚未确定时保留动作未知，并对必要信息进行澄清。不能为了满足固定类别猜测动作，也不能把未知动作当成其他动作。

明确给出备选动作并允许后续选择时，各备选动作本身是已知的，应保留其互斥关系和适用前提。尚未选择不等于动作含义未知，不因此使用未知动作或要求用户重新选择。

具体取值与归类对照见附录 B。

## 4.6 全局要求、局部要求和禁止事项

需要按实际作用范围保留要求：

- 总预算、整体截止时间等，适用于整个请求。
- 字数、格式、局部修改范围等，适用于对应意图。
- 全程禁止的行为，作为全局禁止事项。
- 只在某个阶段生效的禁止，作为该阶段的局部要求。

需要保留硬性限制、软性偏好和可选事项的区别。“尽量”“必须”“最多”“必要时”等词不能在整理中被丢弃或互相替换。

## 4.7 顺序、条件和分支语义

用户明确要求先后时，意图数组按该顺序排列，不增加 `after` 字段。

未指定先后时，按表达顺序展示，不把数组位置解释为用户明确要求的依赖。用户明确表示没有先后要求时，应保留这一要求。

条件分支、互斥选择、并行或独立处理的要求，需要完整保留在有关意图的要求中。不能因为多个条目出现在数组里，就默认所有分支都要执行。

“且”“或”“任一”“全部”“除非”等关系，以及嵌套条件，必须保留原意。本模块不将这些语义转换成实际执行图。

## 4.8 状态、原因与澄清问题

需要区分以下情况：

- 意图明确，没有尚未解决的理解、确认或条件要求。
- 存在影响理解的缺失信息、歧义或冲突。
- 用户明确要求确认后才能继续。
- 用户明确要求满足条件后才能处理。

每条意图的非就绪状态需要有原因说明。需要澄清时，问题直接放在该意图内，可以有多个问题。动作或对象尚未明确时，仍保留已经确定的内容。

澄清问题只针对影响需求理解的内容。缺少日志、代码或执行工具，不必然意味着意图不明确；扩展字段的必填要求，也不自动成为所有用户请求的业务前提。

同一意图同时存在多个前提时，状态按约定优先级展示，完整前提全部保留。状态归类不是实际流程中的第一个待办事项，也不表示已具备执行条件。

用户明确允许后续处理方在给定范围内选择时，需要保留这一要求，不因尚未指定唯一选项而机械地澄清。真实缺失信息仍按其影响处理。

## 4.9 可选上下文理解

调用方可以提供与本轮请求有关的上下文，用于理解指代、方案选择、确认、纠正、撤回和续接。

需要区分用户要求、助手建议、引用资料和历史事实。助手提出方案不等于用户采纳，也不能替用户作出确认。

本轮明确的新要求优先于适用的旧要求。旧要求只有在仍然相关且未被撤回或替换时才参与理解。

结果表达依据本轮及相关上下文确定的当前有效请求，不默认返回整个历史需求的待办清单：

- 补充或调整未完成请求时，表达本轮实际影响的有效意图及仍适用的约束。
- 针对已完成结果提出新要求时，表达实际新增请求，不重放已完成动作。
- 明确要求继续某个未完成请求时，可以表达该请求仍待处理的部分。
- 缺少完成记录，不等于已经确认历史动作未完成。信息不足且影响续接范围时，需要澄清。
- 确认必须能够对应具体对象、方案和范围，不能扩大到其他历史请求。

扩展信息与默认意图采用相同的本轮有效范围，不带回无关历史业务值。模块不自行维护或核实执行状态。

## 4.10 原始输入与整理后输入

原始文本需要原样返回，保留原有措辞、数值、标识和格式。

整理后的文本需要清楚表达本轮有效需求。可以整理口语、明确的错别字和重复表达，依据明确上下文补全指代，并体现明确的纠正结果。

整理后文本仍需保留对象、数值、单位、范围、否定、条件、例外、确认前提和交付要求。未解决的模糊内容需要明确标注，不能改写成已经确定的信息。

整理后的文本不是新增授权或新增任务的来源。所有意图与扩展信息仍以原始文本和相关上下文为依据。

## 4.11 原生 schema-dsl 扩展定义

调用方使用原生 schema-dsl 定义扩展信息。

名称对应字段；类型和约束由 Schema 表达；含义、示例、反例和禁止事项通过描述说明。不再增加一套独立的自定义字段注册结构。

V1 的扩展提取需要覆盖文本、数值、真假值、限定取值、对象与列表及其嵌套、必填与可选、允许为空，以及明确的文本长度、数值范围、列表长度和内容要求。多对象及其对应关系由扩展定义承载。

字段定义解释需要提取什么，不代表用户已经提供了其中的示例或作出了默认业务选择。描述可以帮助理解领域词汇，但不能凭空产生新的默认意图、确认或业务事实。

需要外部资料、实际执行结果或其他本期未提供的信息才能判定的定义，不能被宣称为已经满足。无法适用于本期提取与选择范围的定义，应明确反馈，不静默忽略。

扩展定义集中管理，便于重复使用和按次选择，不表示每次必须提取全部内容，也不表示 schema-dsl 的所有表达都自动适用于本模块。

## 4.12 按次选择扩展信息

调用时fields 属性直接使用字段名称数组：

- 省略或传入 `undefined`：尝试提取全部已定义扩展字段。
- 传入名称数组：只提取指定扩展字段。
- 传入空数组：不提取扩展字段，默认意图结果完整返回。
- 未提供扩展定义时：省略选择或传空数组均只返回默认信息；选择不存在的名称仍需明确反馈。

V1 按顶层字段名称选择，不支持直接选择嵌套子路径。选择对象或列表字段时，按该字段的完整定义处理其内部信息。

字段选择只改变业务扩展信息的范围及相关提取反馈，不改变对用户原意的默认表达。同一输入、上下文和配置下，选择全部、部分或不选择时，默认意图的语义应一致。

所选信息与未选信息存在关联要求时，可以使用原文及相关上下文已经明确的关联依据，但不因此返回未选字段。缺少必要依据时不能宣称关联要求已通过。

## 4.13 结构化结果的语言

未配置语言时，结构化说明使用英文 `en`。调用方可以显式配置中文 `zh-CN`。

配置语言只控制结构化说明，不决定最终面向用户的回复、报告或其他交付物的语言。用户要求交付物使用某种语言时，将其作为对应意图的要求保留。

固定字段名、动作与状态枚举、标识不随配置语言变化。扩展业务值遵守 Schema 和原始含义，不强制翻译名称、编号或枚举值。

用户要求原样保留的文字，以及路径、命令、代码片段、标识和匹配字符串等精确内容，保持原值。这一保护适用于整理文本、对象、要求及扩展信息等所有相关部分。

# 5. 使用方式

应用或其他模块收到用户请求后，通过意图模块明确本轮需求。

通常，调用方提供本轮原始文本即可。如果用户说“按上次的改”“选择方案 B”或“继续刚才的任务”，调用方再提供能够解释这些表达的上下文。

调用方根据本次业务需要，选择提取全部、部分或不提取扩展信息。模块返回统一的默认结果及所选扩展信息。

调用方可以查看原文和整理后的文本，理解主要目的及各条意图，发现限制、前提和待澄清问题，并将结果交给后续处理方。是否询问用户、是否满足前提、是否具备执行能力及如何实施，由后续处理方负责。

常见使用场景包括：

- 一个明确目标，需要直接得到统一表达。
- 一个请求包含分析、方案、修改、测试等多个明确动作。
- 本次只需要提取某个订单编号或项目名称。
- 本次不需要任何扩展字段，只需要默认意图信息。
- 需要结合前文理解选择、确认、纠正或撤回。
- 需要看清模糊表达中已经理解与尚未明确的部分。

# 6. 规则与约束

## 6.1 本轮请求与信息来源

1. 背景愿望不能自动升级为本轮待执行动作。
2. 历史已完成行为不能重新生成待执行意图。
3. 引用、假设、案例、第三方意见和对动作后果的询问，不自动变成执行要求。
4. 用户明确采纳某份资料或方案中的要求时，保留其实际采纳范围。
5. 用户当前表达不能自行修改调用方配置的结构化语言、Schema 或本次字段选择。
6. 本模块不自动保存长期偏好，也不自动加载外部上下文。
7. 委婉表达和疑问句也可能是实际请求。“能帮我整理报告吗”可以表达生成请求，不能仅按句式当成能力询问。
8. 对只有问题描述的输入，根据明确相关上下文判断是否在求助。缺少请求依据时保留事实描述，不仅因出现故障而生成修改、删除或发布动作。
9. 已经确定存在请求、但具体动作仍不明确时，保留动作未知并澄清；不能等同于没有意图。
10. 补充、修改与继续按第 4.9 节确定当前有效范围，不重放无关历史动作。
11. 用户明确允许后续处理方在给定范围内选择时，保留选择空间，不自动当成信息缺失，不扩大允许范围，也不由本模块假装已经完成选择。
12. Schema 的描述、示例、反例和默认业务值不是用户提供的事实，不自动产生新的默认意图。

## 6.2 纠正、撤回、例外和冲突

1. 明确的自我纠正，保留纠正后的有效意图。
2. 本轮撤回的动作不再作为待执行动作。
3. 跨轮撤回需要表达撤回请求本身，不能擅自理解成撤销已经完成的实际结果。
4. 明确例外应保留其适用对象和范围。
5. 无法同时满足的明确要求，需要指出冲突并澄清，不能自行挑选其中一条。
6. 单纯有多个目标或对象，不必然构成冲突。

## 6.3 要求的完整性与作用范围

1. 全局预算不能复制成每条意图独立的预算。
2. 局部限制不能扩大成整个请求的永久禁止。
3. 软性偏好不能当成硬性限制；可选事项不能当成必做事项。
4. 来源、目的地、操作者、接收方、新旧值及对象关系，必须按原意保留。
5. 数量、筛选范围、比较对象和排除项不得被简化丢失。
6. 没有明确提供的时间、币种、单位、对象、路径和业务值不得补造。
7. 可以保留“明天”“上午”等相对表达；没有必要依据时不擅自变成具体日期或时区。

## 6.4 顺序与复杂关系

1. 明确先后通过数组顺序表达。
2. 没有明确先后时，数组位置仅作为展示顺序。
3. 明确的独立、并行、互斥和条件要求保留在相关意图的要求中。
4. 不用数组位置替代条件判断，不把互斥分支理解为全部执行。
5. 完整保留条件的且、或、否定及嵌套关系。
6. V1 负责保留可理解的关系语义，不负责生成可直接调度的执行关系图。
7. 同一动作被明确要求在不同阶段重复时，需要分别保留，不能在整理时合并丢失。
8. 持续时间、频率、次数和停止条件需要保留。例如“每小时检查，直到恢复”为请求要求，本模块不据此自动创建或执行定时任务。
9. 备选动作属于不同类别时，分别保留各自已知类别及互斥选择前提；尚未选择的分支可表达为 conditional，不因为等待后续判断而当作需要澄清。

## 6.5 状态与多个前提

动作和状态的具体取值见附录 B。

同一意图的状态因素同时存在时，按以下优先级进行状态归类：

`needs_clarification` → `awaiting_confirmation` → `conditional` → `ready`

该顺序只用于展示，不决定实际流程中的第一个待办事项，不覆盖任何前提，也不是执行入口。

- 需要澄清时，原因和问题列表均需提供。
- 等待确认时，说明需要确认的具体动作或方案。
- 条件未满足或无法确定是否满足时，保留具体条件。
- 就绪表示意图在当前信息下没有尚未解决的上述问题，仍需遵守顺序、全局要求和局部要求。

例如“先测试，测试通过后让我确认再发布”：发布可以按优先级显示等待确认，但不能因此推断测试已通过或当前应立即发起确认。

确认必须对应适用对象、方案和范围。既有确认不能自动套用于替换后的方案；本轮明确采纳并要求实施时，不能无依据地重复要求同一次确认。

模块依据提供的信息表达前提，不自行核实真实测试结果、权限或系统状态。

## 6.6 澄清规则

1. 问题属于哪条意图，就放在哪条意图里；不新增顶层澄清字段。
2. 一条意图可以有多个独立问题。
3. 候选答案必须有输入或上下文依据；没有候选时使用空列表。
4. 同一缺失信息影响多条意图时，各条意图保留相应影响，展示方可以合并问题。
5. 一条意图缺少信息，不应让其他明确意图一起被标记为需要澄清。
6. 没有源码路径、日志或执行工具，不自动触发澄清。
7. 动作或对象无法确定时保留未知，不猜测动作类别或对象名称。
8. 等待确认已经理解的动作，不等于意图有歧义。
9. 明确允许选择不等于缺少唯一答案；没有逐个列出对象也不必然需要澄清，应判断是否已给出范围和选择要求。
10. 只提供模糊约束、无法关联实际请求时，保留未明确之处，不为承载问题虚构意图。可以关联到真实意图时，再在相关意图内澄清。
11. 扩展定义要求了与当前请求无关的信息，或无法承载多个已明确对象时，不通过追问强迫用户改变真实需求。

## 6.7 扩展信息与校验边界

1. 扩展信息针对本轮有效请求，只使用与本轮相关的信息。
2. 仅返回所选顶层字段。选择嵌套对象或列表时整体处理，不支持直接选择子路径。
3. 未选字段的必填要求不应被当成本次选择缺失，也不能据此强制回填或返回未选字段。
4. 可选字段没有足够依据时省略，不编造或擅自填入默认业务值。
5. 只有定义允许 null 且原文或相关上下文明示为空时，才返回 null；未知不自动等同于空值。
6. 同一单值字段对应多个明确值且缺少选择依据时，不能任选、拼接或改变类型，也不能要求用户删掉真实对象来迁就定义。
7. 多对象及其关联信息由调用方的扩展定义承载。
8. 未知字段名称应明确反馈；重复选择不产生重复业务结果。
9. 结构合法不能替代含义正确。否定、纠正、上下文和对象关系均需与原意一致。
10. 所选字段自身的类型与约束需要满足。涉及关联要求时，可以使用未选但已明确提供的信息作为判断依据，不因此返回该信息。
11. 缺少必要关联依据、定义不适用于部分选择，或当前输入无法满足定义时，明确说明问题，不宣称定义已经满足。
12. 用户只授权后续处理方选择、尚未作出唯一选择时，不将本模块任选的值冒充用户已作出的选择。
13. 字段定义的示例、反例、描述与默认业务值不能代替用户事实，也不自动增加动作。
14. 默认意图明确但扩展提取无法满足定义时，保留已经可靠识别的默认结果及必要澄清，同时明确反馈扩展问题。该结果不能被标成扩展已全部成功。
15. 扩展字段“必填”不自动成为默认意图的业务前提；是否澄清取决于缺失是否影响用户请求的实际含义。
16. 具体失败反馈形式由后续响应设计确定，但必须让调用方区分用户信息不足、定义不能承载或不适用，以及处理未完成等情况。

## 6.8 原文与整理规则

1. 原始文本原样保留，不翻译或清理后冒充原文。
2. 整理结果只做需求理解层面的表达，不新增实现方案或处理步骤。
3. 与需求相关的事实、对象、范围、限制和前提不能被摘要删掉。
4. 明确的纠正可以整理为最终有效需求，原始纠正过程仍在原文中保留。
5. 名称、编号、数值和单位保持准确，不把编号当数量或去掉编号中的前导零。
6. 无依据的错别字修正不得改变人名、项目名、标识或业务含义。
7. 未明确的表达可以标注尚未明确，不能整理成确定事实。
8. 否定范围必须准确。“不必全部删除”不等于“任何内容都不能删除”。
9. 原样文字、路径、命令、代码片段、标识及匹配字符串等精确内容，在所有相关字段中保持原值。整理和翻译说明不能改变这些内容。

## 6.9 语言规则

1. 未传语言或语言配置为 `undefined` 时，默认结构化语言为 `en`，即英文。
2. 显式语言必须为登记有效且能指定输出语言的 BCP 47 标签；非法标签及 und、mul、zxx、纯私有标签明确反馈，不静默回退。
3. 原始输入保持原文。
4. 整理后的输入、目的、对象说明、要求、禁止说明、状态原因和澄清问题，使用配置语言或默认英文。
5. 固定字段名、动作和状态枚举、标识不翻译；动作未知使用空值，不生成本地化的新动作类别。
6. 扩展信息遵循 Schema；固定业务值、名称和编号保持实际值。
7. 用户要求原样的文字及其他精确内容，按第 6.8 节保护。保护范围不局限于 data。
8. 用户要求“用中文写报告”，默认英文结构化时，应以英文说明报告需要用中文，而不是把交付语言改成英文。
9. 候选项中的固定业务值和名称保持实际值。
10. 结构化语言不推断地域、时区或币种，也不自动跟随每次输入语言变化。

## 6.10 无意图与异常边界

没有操作意图时允许返回空意图列表，例如感谢、寒暄、没有求助依据的事实陈述或仅提供限制。

只有模糊限制、又无法关联到实际请求时，保留限制及其尚未明确之处，不创建虚构动作，也不声称限制已明确。能依据上下文关联实际请求时，按该请求的有效范围处理。

已经提出请求但动作未知，使用未知动作表达并澄清，不等同于空意图。动作明确但类别未覆盖时使用其他类别。系统是否支持该动作，不由动作类别判断。

需要区分以下情况：

| 情况 | 行为要求 |
|---|---|
| 信息缺失影响请求理解 | 保留已知部分，只对受影响的意图澄清 |
| 请求明确，但扩展字段缺失、冲突或无法承载原意 | 保留可靠默认结果，明确反馈扩展问题，不伪造满足定义的业务结果 |
| 入参非法、未知选择名称或不适用的定义 | 明确说明参数或定义问题，不包装成完整成功 |
| 输入过长、处理失败或结果非法 | 明确反馈未完成或失败，不静默截断或伪装成功 |

空白输入需有可理解的反馈，不作为已理解请求。本稿不指定资源上限、异常结构或调用实现方式。

# 7. 输入与输出要求

## 7.1 输入信息

概念层面的输入包括：

- 用户本轮原始文本。
- 可选的相关上下文。
- 本次需要提取的业务扩展信息选择。
- 已配置的结构化语言。
- 可选的原生 schema-dsl 扩展定义。

上下文用于帮助理解，不代替本轮原文，也不等于自动重新执行历史任务。

## 7.2 输出信息

| 输出部分 | 需要表达的含义 |
|---|---|
| 原始输入 | 本轮文本原文 |
| 整理后输入 | 保留原意、体现未明确内容的清晰表达 |
| 主要目的 | 本轮主要期望结果；无法确定时为空 |
| 全局要求 | 整个请求适用的预算、时间、范围或其他要求 |
| 意图列表 | 本轮有效请求、已知或未知动作、对象、局部要求和理解状态 |
| 非就绪原因 | 当前需要澄清、确认或满足条件的原因 |
| 澄清问题 | 与各条意图有关的问题及有依据的候选答案 |
| 全局禁止 | 整个请求明确禁止的行为 |
| 业务扩展信息 | 所选 Schema 字段对应的结果 |
| 必要的问题反馈 | 扩展信息是否满足定义、无法满足的原因，以及入参或处理问题 |

默认部分保持稳定含义。扩展信息为空，不表示默认部分也应为空。

没有主要目的使用空值；没有意图、要求或禁止事项使用空列表；不提取扩展信息时使用空对象。动作未知使用空值。未到需要澄清的状态时，不返回无意义的空问题结构。

扩展无法满足定义而默认信息可靠时，应保留可靠默认信息并同时反馈扩展问题；不能仅返回空 data 让调用方误以为全部成功。入参或处理本身未完成时，也不能伪造完整默认结果。

具体字段名和普通完整响应在附录记录。必要问题反馈的具体结构留给后续响应设计，本稿不提前增加异常字段或包装结构。

# 8. 范围边界

## 8.1 V1 包含

- 默认英文或显式中文的结构化说明，以及可选的原生 schema-dsl 扩展定义。

- 自动询问用户、替用户确认或修改调用方配置。
- 决定最终面向用户的回复语言。
- 在识别阶段替用户补出实施任务。
- 用一个当前状态替代所有前提，或用数组位置替代完整条件语义。
- 新增完整产品规划、商业规划、技术架构或技术选型。

## 8.3 后续范围

# 9. 最终预期

功能完成后，调用方能够：

1. 用同一套配置重复处理用户请求，按次选择业务信息。
2. 同时看到用户原文和清晰整理后的需求，检查理解是否准确。
3. 理解本轮主要目的、各条动作和对象，而不被背景、引用或旧任务误导。
4. 看清全局与局部要求，保留数值、范围、否定、例外和条件。
5. 区分需要澄清、等待确认和条件未满足，不把这些情况混为执行失败。
6. 在多前提共存时，不因状态切换丢失其他要求。
7. 获得符合所选业务定义的信息；扩展无法满足定义时，继续获得可靠默认结果及明确的问题反馈。
8. 通过默认英文或显式中文理解结构化说明，精确原值及交付语言要求保持原意。
9. 把结果交给后续模块使用，而不误以为操作已经执行或权限已经验证。

# 附录 A：已确认的配置与调用约定

本附录记录使用要求，不代表存在已经发布的同名 SDK，也不规定导出路径或技术实现。

## A.1 配置示例

下面显式使用 `zh-CN`，因此 C.1—C.4 的说明文本为中文。默认语言是 `en`，不因这些中文示例改变。

```js
import { s } from "schema-dsl/pure";

const intent = new Intent({
  language: "zh-CN",

  schema: s({
    projectName: s("string").description(`
      用户本轮请求涉及的项目名称。
      示例：“修复 order-service 的问题”，提取为“order-service”。
      反例：“修改订单查询模块”，其中“订单查询模块”不是项目名称。
      禁止自行生成或补全；没有足够依据时不填写。
    `),

    issueType: s("查询失败|登录失败|其他").description(`
      用户主要希望解决的问题类型。
      示例：“订单查不出来”，提取为“查询失败”。
      反例：“查询登录日志”，不能提取为“登录失败”。
      “其他”用于明确存在但不属于查询失败或登录失败的问题。
      注意否定、纠正和上下文；没有明确问题时不填写。
    `)
  })
});
```

配置语言只控制结构化文本。上述业务枚举不因配置语言变化而变成其他值。

## A.2 请求语义（最新约定）

唯一调用形式为 intent.parse({ input, fields, context })。

| 属性 | 含义 |
|---|---|
| input | 必填，本轮原文 |
| fields | 省略或 undefined 尝试全部顶层字段；数组选择指定字段；[] 只返回默认信息 |
| context | 可选字符串或按顺序排列的 user/assistant/tool 消息数组；不自动加载历史 |

旧位置式签名不再适用。[] 不让默认响应为空；未知顶层字段明确失败。

## A.3 上下文示例

以下使用按发生顺序排列的对话记录，说明上下文如何辅助理解，不要求调用方自动加载历史。

```js
const context = [
  {
    role: "user",
    content: "分析 order-service 的登录失败问题，先给方案，未经我确认不要修改。"
  },
  {
    role: "assistant",
    content: "方案 A：调整超时配置。方案 B：修复令牌刷新逻辑。"
  }
];

const input = "选择方案 B，按这个方案修改。";

const result = await intent.parse({ input, fields: ["projectName"], context });
```

这次选择已经明确采纳方案 B，不能继续把方案 A 当成本轮任务，也不能只因为旧消息写着“未经确认”就忽略本轮明确的确认。

如果当前表达无法对应具体方案，例如存在多组方案而用户只说“确认”，则需要澄清。

## A.4 默认英文与可选 Schema

```js
// 省略 language 与 schema：默认英文，只返回默认意图信息
const defaultIntent = new Intent({});

await defaultIntent.parse({ input });
await defaultIntent.parse({ input, fields: [] });
await defaultIntent.parse({ input, context });

// 仅使用中文默认意图，不配置扩展
const chineseIntent = new Intent({ language: "zh-CN" });

await chineseIntent.parse({ input, fields: [], context });
```

未提供 Schema 时，省略字段选择与空数组都得到完整默认结果，data 为 `{}`。若选择不存在的字段名称，应明确反馈选择问题。

Schema 配置存在但语言省略时，同样默认英文；业务值按定义保持原值，不被统一翻译。

# 附录 B：默认响应与完整枚举

## B.1 根级字段

| 字段 | 含义 | 无相关内容时 |
|---|---|---|
| `input` | 本轮原始文本，原样保留 | 非法空白输入需明确反馈 |
| `normalizedInput` | 根据原文及相关上下文整理的本轮有效需求 | 可以说明没有操作请求，不创造任务 |
| `primaryIntent` | 本轮主要目的 | `null` |
| `requirements` | 整个请求适用的要求 | `[]` |
| `intents` | 本轮有效意图列表 | `[]` |
| `prohibitions` | 全局禁止事项，保留范围和例外 | `[]` |
| `data` | 本次所选业务扩展信息 | `{}` |

## B.2 意图字段

| 字段 | 含义与规则 |
|---|---|
| `id` | 当前响应内唯一标识，不保证跨调用稳定 |
| `action` | 动作明确时使用七个固定类别之一；动作尚未确定时为 `null` |
| `target` | 动作对象与必要范围，未知时为 `null` |
| `requirements` | 用户明确提出的局部要求、业务动作细节和全部处理前提；没有则为 `[]` |
| `status` | 意图理解及已表达前提的状态归类，不代表执行入口或实际进度 |
| `reason` | 所有非 `ready` 状态必填；`ready` 时省略 |
| `clarification` | 仅在 `needs_clarification` 时出现，至少一个问题 |

全局要求不必复制到每条意图；它们仍然适用于相应动作。

## B.3 澄清字段

`clarification` 是数组，每项包含：

| 字段 | 含义 |
|---|---|
| `question` | 具体需要询问的问题 |
| `options` | 有输入或上下文依据的候选答案；没有则为 `[]` |

不再增加 `required` 或 `intentIds`。状态已经说明是否需要澄清，所在意图已经说明问题归属。

## B.4 action 完整取值

| 值 | 含义 | 示例 |
|---|---|---|
| `query` | 查找、读取或获取已有信息 | 查询订单、读取配置 |
| `analyze` | 分析、比较、评估或判断 | 分析原因、审查需求、比较方案 |
| `generate` | 生成新的内容、表达或总结 | 编写方案、生成报告 |
| `modify` | 修改已有内容、配置或状态 | 修改代码、更新状态 |
| `delete` | 删除指定内容或资源 | 删除文件、删除记录 |
| `execute` | 运行命令、程序或明确的操作任务，不作为所有副作用动作的兜底 | 运行测试、执行脚本、发布操作 |
| `other` | 动作明确但不能归入以上类别 | 当前通用分类未覆盖的明确动作 |

`other` 不是“未知意图”，也不是“不支持”。业务细节不能因通用类别丢失。

除以上七个动作枚举外，允许 `action: null` 表达已经存在请求、但动作未知。此时必须为 `needs_clarification`，提供原因及非空澄清问题；对象已知则保留对象。空值不是第八个动作类别。

`null` 表达无法理解用户请求的具体动作，不表达已明确给出、仅等待后续选择的备选动作。后者保留已知动作及其互斥前提，见 C.11。

## B.5 status 完整枚举

| 值 | 含义 | reason | clarification |
|---|---|---|---|
| `ready` | 意图明确，没有尚未解决的澄清、确认或条件要求 | 省略 | 省略 |
| `needs_clarification` | 有影响理解的缺失、歧义或冲突 | 必填 | 必填，非空数组 |
| `awaiting_confirmation` | 有尚未满足的用户确认要求 | 必填 | 省略 |
| `conditional` | 有尚未满足或无法判断是否满足的条件 | 必填 | 省略 |

这些是意图理解状态，不包含 `running`、`completed`、`failed` 等实际执行进度。

配置语言不翻译以上枚举值。

## B.6 动作归类对照

按用户要求达到的直接结果归类。能明确归入专门类别时，不因为存在实际操作就统一使用 `execute`。

| 用户请求 | action | 需要保留的具体含义 |
|---|---|---|
| 查询已有订单信息 | `query` | 查询范围、对象及筛选条件 |
| 比较两笔订单的变化 | `analyze` | 比较对象与评估要求 |
| 生成新的报告或脚本内容 | `generate` | 内容、格式和交付要求 |
| 替换已有报告的结论 | `modify` | 被替换的内容及新内容要求 |
| 取消订单 | `modify` | 将指定订单取消，而非任意修改订单 |
| 重命名或移动已有文件 | `modify` | 原对象、新名称或目的地，保留方向 |
| 删除指定文件或记录 | `delete` | 删除范围与排除项 |
| 运行脚本、测试或发布操作 | `execute` | 具体运行或发布要求及全部前提 |
| 发送已有邮件 | `execute` | 保留接收方及内容；不补出生成邮件步骤 |
| 将已有工单转交给其他处理方 | `modify` | 保留工单与新处理方，表达归属或处理状态的变化 |
| 新建不能归入内容生成的业务对象 | `other` | 如创建业务订单，保留“创建”的实际含义 |
| 撤回先前尚待处理的请求 | `modify` | 改变请求的有效状态，不等于回滚已完成结果 |
| 请求存在，但不知道要做什么 | `null` | 保留已知部分，并澄清动作 |

分类不增加用户未提出的步骤。分析产生结论、查询产生信息，不因此另外增加“生成”意图；仅在用户明确提出额外交付或独立动作时分别保留。

## C.10 扩展问题与可靠默认结果共存

| 输入及扩展定义 | 默认结果要求 | 必须同时反馈的扩展问题 |
|---|---|---|
| 查询那笔订单的状态，但原文与上下文没有对象；所选订单编号必填 | 保留 query 意图、对象未知及必要澄清 | 订单编号缺失，当前所选信息无法满足定义 |
| 总结已提供的文字；所选字段却要求必填订单编号 | 总结意图保持明确，不询问与总结无关的订单 | 当前输入没有订单编号，扩展要求无法满足；不能当作总结意图不明确 |
| 取消订单 A，查询订单 B；只定义单个订单编号 | 保留取消 A 和查询 B 两条真实意图 | 单值定义无法完整承载两个对象；不能任选，也不要求用户放弃其中一个 |
| 用户允许后续从 A、B 选择；所选字段要求当前唯一选择 | 保留允许选择的范围，不能重复要求用户作决定 | 尚未发生的选择不能被当成用户已提供的单值 |
| 只选择结束时间，关联要求需要开始时间且未提供 | 默认意图按原意保留；真正影响意图时才澄清 | 关联依据不足，不能宣称结束时间已经满足全部关联要求 |

调用方必须能够同时获得可靠默认结果和扩展未满足的说明。仅有普通成功示例中的空 data，不足以表达这类结果。

## F.3 技术方案需要完成的设计事项

以下事项有明确需求依据，可以在技术方案中决定，无需继续扩写需求概况：

- 模块如何取得理解与提取能力，以及相应的接入和调用配置。
- 上下文的具体可接受形式及非法入参的反馈约定。
- 扩展定义的受支持表达、部分选择和关联要求的具体适用约定。
- 扩展未满足、可靠默认结果及处理失败的完整响应反馈形式。
- 输入与输出长度、超时及其他资源限制的具体数值。
- 如何检查默认结果保真、扩展结果正确、场景组合一致，以及真实识别效果。

技术设计不能改变已确认语义：不能将空数组解释为空响应、不能丢弃原文、不能把业务默认值当成用户事实、不能因扩展失败隐藏可靠默认意图，也不能扩大模块执行职责。

## F.4 判断的证据与限度

本次复审检查了需求规则、枚举、完整示例和组合场景的一致性；JSON 示例语法检查只说明示例可解析，语义判断由本轮审查完成。

“可以进入技术方案”表示目标、行为和边界足够明确，可以据此设计。实际识别质量、稳定性和资源表现仍需在后续实现及效果验证中证明，当前没有实际模型运行结论。
